# Three interrupt-remapping properties this harness cannot decide

VT-d Rev. 4.0 (D51397-015) Section 5.1.4: when interrupt remapping is enabled,
"If Extended Interrupt Mode is enabled (EIME field in Interrupt Remapping Table
Address Register is Set), or if the Compatibility format interrupts are disabled
(CFIS field in the Global Status Register is Clear), the Compatibility format
interrupts are blocked."

## 1. Compatibility-format messages are delivered, not blocked

QEMU 11.1.0 `hw/i386/intel_iommu.c:4377-4381` does not do that:

```
    /* This is compatible mode. */
    if (addr.addr.int_mode != VTD_IR_INT_FORMAT_REMAP) {
        memcpy(translated, origin, sizeof(*origin));
        goto out;
    }
```

The message is copied through unchanged. The bit is not merely unconsulted:
`VTD_GCMD_CFI` (`intel_iommu_internal.h:148`) and `VTD_GSTS_CFIS` (`:159`) are
defined and referenced nowhere, and `vtd_handle_gcmd_write`
(`intel_iommu.c:2712-2741`) acts on `TE`, `SRTP`, `QIE`, `SIRTP` and `IRE` and
on nothing else. A guest can neither set `CFIS` here nor clear it: it reads 0
whatever the guest writes.

**So a gate asserting `GSTS.CFIS` is clear cannot fail on this harness.** It is
a statement about the kernel for whoever reads it on hardware, not an
instrument, and `tests/common/iommu.rs` says so where it makes the assertion.

The specification is the one to believe: it is the hardware contract, and the
blocking is the whole security property — without it a device that can write an
`0xFEEx_xxxx` DWORD injects any vector at any CPU, which is what interrupt
remapping exists to stop.

Measured, both arms, on the branch that turned interrupt remapping on. One
source at a time was left in compatibility format with `IRE` set and `CFIS`
clear, and the device went on working:

- the i8042's keyboard pin (GSI 1) left as a compatibility redirection entry:
  `PASS  i8042_keyboard  (6s)` — typed input still arrived.
- virtio-net's MSI-X (vector `0x22`) left at the compatibility address:
  `PASS  netd_hostile_peer  (4s)`, with `netd hostile peer: 6 malformed frames
  refused, 32 of 48 unidentified connections held, silent one dropped after
  2004 ms, netd alive` — real traffic still moved.

Consequences, which is why this is filed rather than noted:

- **A source nobody moved to the remappable format is invisible to every
  behavioural test in this suite.** It works on QEMU and black-screens on real
  hardware. `iommu_interrupt_remapping` is the only instrument in reach that can
  see one, and it sees it by reading the redirection entry and the MSI address
  back off the chip; it reds on both mutations above, naming the source.
- **The harness cannot certify the protection.** That a rogue device cannot
  inject a vector is unmeasurable here for the same reason. It is answerable on
  the T14 and nowhere else.

## 2. The fault event's exemption is undecided here, in either direction

Section 5.1.6 says interrupts generated by remapping-hardware events are not
subject to remapping, which is why `vtd/fault.rs:18` writes the compatibility
address at `:84` and this branch left it alone.

That the fault line still arrives with `IRE` set is **not** evidence the
exemption holds. QEMU delivers the fault event by calling
`apic_get_class(NULL)->send_msi(&msi)` directly (`intel_iommu.c:473`, reached
from `vtd_generate_fault_event` at `:480`), so the message never enters the
interrupt-remapping path at all — and by item 1 it would be passed through even
if it did. `iommu_context_absent` and `iommu_empty_domain` going green under
`IRE` is consistent with the exemption holding *and* with QEMU blocking nothing,
and a harness that cannot separate two hypotheses has not tested either.

This was written up once as measured and it was not. The same inference was
correctly refused about `CFI` in item 1 and then made in the other direction
about this; the record is corrected rather than quietly dropped, because the
false version was in a commit message before it was in this file.

## 3. Invalidation of the interrupt entry cache is unmeasurable

`vtd_irte_get` re-reads the entry from guest memory on every remap
(`intel_iommu.c:4194-4215`), so QEMU has no interrupt entry cache to go stale,
and `vtd_process_inv_iec_desc` (`:3238`) validates the descriptor and forwards
it to the accelerator's irqchip without any model state of its own. A kernel
that never invalidated would be green here. The invalidation is written because
`CAP.CM` is set and Section 6.4 says such a unit may cache the entry a fault was
taken on; that reasoning is the specification's, not this harness's.

## Exit

All three are answerable on the T14 and nowhere in reach:

1. a same-session A/B showing a compatibility-format message blocked under
   `CFIS=0` — or an upstream QEMU that implements the check;
2. a fault provoked with `IRE` set on real silicon, showing the fault MSI still
   delivered;
3. an entry rewritten under load with and without the invalidation.

A fourth, smaller, belongs with them: **the entry's destination encoding is
exercised but not discriminated.** With `ECAP.EIM` set the kernel writes the
APIC id at `DST` 63:32 and without it at 47:40, and
`Profile::IommuEim` now boots the first branch — but every interrupt on every
machine here targets APIC 0, and 0 encodes identically either way. A non-zero
destination is what would tell them apart, and nothing here has one.

What is owed meanwhile is that no gate is written as though the harness could
decide any of this.
